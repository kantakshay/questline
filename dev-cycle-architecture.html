Dev Cycle: how the platform is built

A learning platform where new developers pick a project, clone it with real git, build it on their own machine, and open, review, and merge a pull request — entirely on our own infrastructure. No GitHub account, no external tools. This page is the reference for how it's put together.

01

Overview

The platform's one architectural bet: don't reimplement git. Real git hosting, pull requests, diffs, and merges are delegated to Gitea, a self-hosted git server we run ourselves. Our own backend and database handle everything Gitea doesn't know about — the course catalog, who's enrolled in what, and the review workflow layered on top of Gitea's PRs.

What's real

Git itself. Students run actual git clone, git commit, git push from their own terminal against a repo we host. The muscle memory transfers directly to a real job.

What's simulated

The destination. There is no GitHub anywhere in the loop — the "pull request" a student opens lives entirely on our platform, reviewed by another student, merged by our backend calling Gitea's own API.

02

Component architecture

Five parts, two of which the student touches directly — their own terminal, and the browser. Everything else is infrastructure we run in Docker Compose.

03

Tech stack

Git hosting
Gitea (Docker, SQLite mode)
Real clone/push/PR/diff/merge over HTTP, plus webhooks and an admin API — without hand-writing the git wire protocol.
Backend
Node.js + Express, JavaScript
REST over GraphQL for this scope — the access patterns are simple CRUD plus a few workflow actions, not deeply nested queries.
Database
DynamoDB (Local for dev)
Multi-table, one table per entity — not single-table design — so the schema stays inspectable while learning DynamoDB.
Frontend
React + Vite, JavaScript
Diffs render client-side with diff2html against JSON the API proxies from Gitea.
04

The pull request lifecycle

This is the mechanism the whole product depends on: the platform never polls Gitea for status — it reacts to webhooks, and only calls Gitea's API to originate an action. Boundary crossings are the whole story.

06

Project catalog

Every project is a spec, not a fixed-language template — students pick whatever language or framework they want. Three tracks, three difficulty levels each.

TrackBeginnerIntermediateAdvanced
FRONTEND Portfolio page, To-do list, Weather dashboard Kanban board, Recipe finder, Expense tracker Realtime collaborative notes, Multiplayer game UI
BACKEND Notes REST API, URL shortener, Auth service Order/inventory API, Rate-limited gateway, Job queue Redis-backed cache service, Event-driven pub/sub pair
FULLSTACK Blog platform, Finance tracker E-commerce store, Mini social feed Realtime collab tool with roles, Multi-tenant SaaS starter

Starter code

Each project can ship optional starter stubs per language (Node, Python, etc.) as separate Gitea template repos. A student without a matching stub starts from a blank scaffold — never blocked by language choice.

Design guidance

Frontend specs include a low-fidelity wireframe — required layout and UI elements only. Colors, branding, and visual polish are left entirely to the student, so review stays focused on function, not taste.

08

Production deployment

Gitea is the one piece that can't be serverless — it owns real repos on persistent disk. Everything else scales to zero when nobody's using it, which fits a bursty, low-volume learning platform far better than paying for an always-on box.

Why Lambda over ECS/EC2 for the API

ECS and EC2 bill by the hour whether a student is using the platform or not — a fixed cost from day one. Lambda bills per invocation, with 1M requests and 400,000 GB-seconds of compute free every month, permanently. For a bursty, low-volume learning platform this keeps the API near $0/month at MVP scale, with less to operate (no cluster, task definitions, or scaling policies). The crossover where a fixed server gets cheaper only happens at sustained high-volume traffic, well past MVP.

PieceWhereWhy
GiteaVPS (Docker), Caddy for HTTPSNeeds persistent disk + a long-running stateful process — can't be serverless.

09

Roadmap

MVP is solo-student, start to merge. Team support is designed for, not built yet.

  • Now: solo enrollment, manual reviewer picker from other students on the same project.
  • Phase 2: Teams / TeamMembers tables; reviewer assignment auto-picks from teammates when a project is team-owned, without reshaping PullRequests.
10

Build order

1
Stand up Gitea + DynamoDB Local
Confirm a real git clone/push works against Compose-hosted Gitea before writing any app code.
2
Backend skeleton
Express app, DynamoDB client, table-creation script, health check.
3
Auth + Gitea provisioning
Register/login; backend creates a matching Gitea user and token per student.
4
Catalog + enrollment
Seed sample projects, fork template repos in Gitea, show the clone URL.
5
Webhooks
Wire Gitea's push webhook; verify delivery in Gitea's own admin log.
6
PR flow, diff, review, merge
Create/list PRs, render diffs with diff2html, comments and decisions, merge via Gitea's API.
7
End-to-end pass
Two accounts, one full loop from start to merge, by hand.
